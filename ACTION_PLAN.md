# Action Plan — EU AI Act Internal Governance Tool

Derived from `REQUIREMENTS.md`. Organized as phases; each item is scoped to be usable directly as a Claude Code prompt. Do the phases in order — later phases depend on data-model, database, auth, and correctness fixes from earlier ones.

---

## Phase 0 — Cleanup (low risk, do first)

1. **Remove/archive stale packaging docs.** Delete or move `00_REVIEW_AND_CORRECTIONS.md`, `15_INSTALLATION_AND_DEPLOYMENT.md`, `16_COMPLETE_PACKAGE_SUMMARY.md` to an `archive/` folder — they reference numbered files that don't exist in the repo and will mislead future readers now that `REQUIREMENTS.md`/`ACTION_PLAN.md` exist.
2. **Remove orphaned route file.** Delete `pages/api/assessments/route.ts` (App Router convention, unused under Pages Router); confirm `pages/api/assessments.ts` is the only handler for that path and all existing tests/UI calls still pass.
3. **Confirm baseline.** Run `npm test` and `npx tsc --noEmit` before making functional changes, so regressions in later phases are attributable.

## Phase 1 — Classification correctness fixes (no UI change yet)

4. **Implement the Article 6(3) exemption check.** In `lib/classification-engine.ts`, add a step between Annex III matching and returning `HIGH_RISK` that evaluates the `article_6_3_exemption` conditions from `rules.yaml`. Since the current input has no fields for this, add new boolean/enum fields to `AssessmentInput` (e.g., `performsNarrowProceduralTask`, `improvesCompletedHumanActivity`, `detectsPatternsWithoutInfluencingDecisions`, `performsPreparatoryWork`, `significantRiskOfHarm`) and use them to decide whether an Annex III match still returns `HIGH_RISK` or is downgraded with the exemption reasoning recorded in the result. Add unit tests for both branches (exemption applies / doesn't apply).
5. **Add `role` as a required structured input.** Add `role: ('provider' | 'deployer' | 'importer' | 'distributor' | 'product_manufacturer')[]` to `AssessmentInput`. Filter/annotate the `obligations` output per selected role(s) instead of returning one fixed obligations list regardless of role. Add tests covering at least provider vs. deployer producing different obligations for the same classification.
6. **Add GPAI systemic-risk sub-classification.** Add fields to capture whether the system is a GPAI model with systemic risk (per Article 51 threshold) and branch the GPAI result into standard vs. systemic-risk obligations. Add tests.
7. **Allow non-exclusive matching where legally correct.** Review the current first-match-wins short-circuit in `classifyAISystem()`; keep Article 5 violations as always-fatal/exclusive, but allow Annex III + Article 50 obligations to combine in one result where both genuinely apply. Add tests for a system that should get both.

## Phase 2 — Persistent database (do this before Phases 3–4 — everything downstream depends on it)

This phase exists independently of *where* the app is hosted. The current `fs.appendFileSync`/`fs.readFileSync` approach in `lib/assessment-log.ts` doesn't survive any stateless/serverless host (Vercel included) and has no audit history — replace it now with a real, externally hosted, persistent database, reachable via connection string or REST API so it works identically whether the app later runs on Vercel, Render, Railway, a company server, or locally.

8. **Choose and provision the database.** Pick one free-tier option and provision it: **Supabase Postgres** or **Neon Postgres** (recommended — users, assessments, sessions, checklist items, and audit events are all relational and you'll want to join/query them, e.g. "every status change for this system's checklist" or "every assessment created by this user"), or Upstash Redis if a simpler key-value store is preferred. Record the connection details as env vars (`DATABASE_URL` or equivalent) in `.env.local` (gitignored) and document required env vars in a short `DEPLOYMENT.md`.
9. **Define the schema.** At minimum: `users` (see Phase 3), `assessments` (current JSONL record shape, extended with `createdByUserId`), `qa_sessions` (draft/in-progress interviews, see item 18), `checklist_items` (evidence checklist current state, see item 16), `audit_events` (append-only history, see item 17). Use a migration tool appropriate to the chosen DB (e.g., Prisma or Drizzle for Postgres).
10. **Replace `lib/assessment-log.ts` internals.** Swap the file-based implementation for the new database behind the **same exported function signatures** (`appendAssessment`, `readAllAssessments`, `getAssessmentById`, `getLatestAssessments`, `searchAssessments`, `getStatistics`, `exportAsJSON`, `exportAsCSV`, `getLogStats`) so calling code (API routes, tests) doesn't need to change. Update/rewrite the existing 40+ log tests against the new backend (mock the DB client rather than the filesystem).
11. **Verify persistence survives a stateless invocation.** Locally, simulate two separate process invocations writing/reading the same data (or deploy a throwaway preview) to confirm state isn't lost between requests — this is the specific failure mode being fixed.

## Phase 3 — Authentication & user management (seed user + managed users)

Replaces "no auth" with a seed-user-administered user model, per the requirement: a pre-provisioned seed user creates other users (email + password); those users log in with those credentials; only the seed user can change another user's password.

12. **Add a `users` table and provision the seed user.** Schema: `id, email (unique), passwordHash, isSeedUser boolean, createdByUserId (nullable, FK to users.id), createdAt, updatedAt`. Provision the seed user's email/password from environment variables (`SEED_USER_EMAIL`, `SEED_USER_PASSWORD`) via a one-time bootstrap/migration script that runs on first setup — never hardcode credentials in source or commit them to git. Hash all passwords with bcrypt or argon2; never store or log plaintext.
13. **Implement login.** Email + password authentication guarding all pages/API routes except the login screen. Use a session-cookie or JWT approach — either a lightweight custom implementation or an open-source library (e.g., NextAuth.js Credentials provider) — no paid auth service required. Login failures must not reveal whether the email exists (generic "invalid email or password").
14. **Seed-user-only user management (no self-service, no SMTP).** Add API routes restricted to the seed user (`isSeedUser === true`) to (a) create a new user by email + initial password, and (b) change/reset any other user's password — including the seed user's own. There is no self-service "change my password" or "forgot password" flow anywhere in the app (no SMTP integration in this MVP, so identity can't be verified by email); non-seed users have no password-management UI at all and receive their credentials out of band from the admin. A non-seed user must get a 403 if it attempts either route — add tests confirming this.
15. **Wire `actorId` to real authenticated users.** Once Phase 4's `QASession` and `AuditEvent` types exist, replace their placeholder `actorId` fields with the logged-in user's `id` from the auth session (item 13), so every assessment, checklist change, and audit event is attributable to a real person, not a placeholder string.

## Phase 4 — Data model: governance structure + evidence checklist + audit trail + sessions

16. **Governance structure + evidence checklist types.** Add a `GovernanceRequirement` type (owner role, review cadence, escalation trigger) mapping `(classification, role)` → requirements, and an `EvidenceChecklistItem` type (id, obligationArticle, title, description, requiredArtifact, status, owner, evidenceLink, lastUpdated) mapping each applicable obligation to checklist items. Wire both into `ClassificationResult`. Persist checklist items in the `checklist_items` table from Phase 2, keyed by system id, with an API route (e.g. `PATCH /api/systems/:id/checklist/:itemId`) to update status/owner/evidenceLink independently of re-running the questionnaire. Require an authenticated user (Phase 3) to make any change.
17. **Append-only audit event log.** Define an `AuditEvent` type (`id, entityType, entityId, actorId, action, previousValue, newValue, timestamp`) and write one row to `audit_events` on every assessment submission and every checklist status/owner/evidenceLink change from item 16 — never update a record in place without also writing the corresponding audit event. Add `GET /api/systems/:id/audit` to read full history for a system. This is required for governance/compliance review, not optional polish.
18. **Q&A session persistence.** Define a `QASession` type (id, actorId, answers-so-far, current step, any LLM exchange from Phase 5 item 23, createdAt, updatedAt) backed by the `qa_sessions` table, so a partially completed interview can be saved and resumed rather than lost on navigation/refresh. Add `POST /api/sessions` (create/update draft) and `GET /api/sessions/:id` (resume) routes, scoped to the authenticated user who owns the session.

## Phase 5 — Adaptive Q&A UI (replaces static form)

19. **Design the step sequence.** Build the multi-step flow described in `REQUIREMENTS.md` §3.1 (AI-system gate → product characterization → role → sector-specific questions → Article 5 screening → Article 6(3) exemption questions if applicable → geography/vulnerable groups → free text) as a wizard in `pages/dashboard.tsx` or a new `pages/assess.tsx`, replacing the current single static form. Persist progress into a `QASession` (Phase 4 item 18) as the user moves between steps. Keep each step's fields typed against the `AssessmentInput` additions from Phase 1.
20. **Conditional/branching rendering.** Only show sector-specific and exemption questions when a prior answer makes them relevant (e.g., Annex III category selected → show that category's sub-questions; Annex III matched → show Article 6(3) exemption questions).
21. **Result screen redesign.** Update the results view to show: classification + reasoning trace, applicable articles, the governance-structure block (owner/cadence/escalation), and the evidence checklist (with status controls wired to the Phase 4 API), not just a flat obligations list.
22. **PDF export (Q&A + inference + checklist as one timestamped document).** Add a "Download PDF" action on the result screen and on a saved system's history view. Use a free/open-source generator (`@react-pdf/renderer`, `pdf-lib`, or headless-Chromium print-to-PDF) to render one document containing: the submitted Q&A answers, the classification/reasoning trace, the governance structure block, and the evidence checklist's current status/owner/evidence links — pulled live from the Phase 2/4 database at request time. Stamp the document itself with a generation timestamp (distinct from the original assessment timestamp, since checklist state can change after the assessment ran). Add a corresponding API route (e.g. `GET /api/systems/:id/report.pdf`), authenticated, rather than generating client-side, so the data pulled is always current server-side state. Filename: `<systemName>-compliance-record-<YYYY-MM-DD>.pdf`.
23. **(Optional) LLM-assisted intake.** If pursuing REQUIREMENTS.md §3.6: add a server-side call that takes the free-text description and suggests structured-field values for the user to confirm/edit before submission, storing the exchange in the `QASession`. The LLM output must only pre-fill suggested answers — the deterministic engine from Phase 1 still computes the final classification from the confirmed structured answers.

## Phase 6 — Deployment (Vercel or elsewhere) and smoke test

24. **Deploy and confirm end-to-end.** Deploy to the chosen host (Vercel or otherwise) with the Phase 2 database's env vars and Phase 3's `SEED_USER_EMAIL`/`SEED_USER_PASSWORD` configured, then run the full flow end-to-end against the deployed instance: log in as the seed user, create a second user, log in as that user, confirm a session can be resumed, an assessment persists and is retrievable, checklist status updates are visible in the audit log with the correct actor, the PDF report downloads correctly, and stats/export endpoints work against the new store.
25. **Post-deploy credential hygiene.** Confirm the seed user's initial password from `SEED_USER_EMAIL`/`SEED_USER_PASSWORD` is changed immediately after first login (the seed user uses their own admin password-change route from Phase 3 item 14 to reset it), and that no credentials are committed to git, logged anywhere, or sent by email (no SMTP integration exists to do so).

26. **Update/extend test suite** to cover every new function from Phases 1–5 (exemption logic, role filtering, GPAI systemic-risk branch, governance mapping, checklist mapping, audit event writes, session save/resume, PDF generation, and auth: login, seed-user-only user creation/password-reset, 403 for non-seed attempts). Target keeping the existing 70%+ coverage threshold.
27. **Update `README.md`** to reflect the real current architecture (drop references to the stale numbered-file package structure once Phase 0 archives those docs) and document the database and auth setup from Phases 2–3.
28. **Final acceptance pass** against the checklist in `REQUIREMENTS.md` §6.

## How to use this with Claude Code

Each numbered item above is scoped to be one Claude Code session/prompt: state the phase and item number, point it at `REQUIREMENTS.md` for the "why," and the relevant source file(s) named in the item for the "where." Do items within a phase in order where they touch the same file (e.g., 4 → 5 → 6 → 7 all edit `classification-engine.ts` and will conflict if parallelized). Phases 0–4 should be sequential (each depends on the previous phase's data shapes); Phase 5 can start once Phase 1's `AssessmentInput` shape and Phase 4's session/checklist APIs are stable.
